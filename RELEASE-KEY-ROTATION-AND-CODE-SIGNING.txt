SMART CAFETERIA - PRODUCTION KEY ROTATION AND CODE SIGNING
================================================================

This document replaces the development licensing keys with production keys,
then Authenticode-signs the published EXE and the MSI.

IMPORTANT ORDER
---------------
1. Generate the production keypair.
2. Replace the embedded public key in the app source.
3. Remove the development private key.
4. Rebuild and test.
5. Publish the Release EXE.
6. SIGN THE EXE FIRST.
7. Build the MSI (so it embeds the signed EXE).
8. SIGN THE MSI.
9. Verify both signatures and record the final hashes.

Do NOT build the MSI before signing the EXE.
Do NOT run "dotnet publish" after signing the EXE; it would replace the signed file.

Paths used below assume this repository:
C:\Users\user\Documents\Smart Cafeteria Desktop

Run the commands in Windows PowerShell 5.1 on the vendor build machine.
Use the dotnet path that works on this machine:

    $root = "C:\Users\user\Documents\Smart Cafeteria Desktop"
    Set-Location $root
    $dotnet = "$env:LOCALAPPDATA\Microsoft\dotnet-sdk\dotnet.exe"
    if (-not (Test-Path $dotnet)) { $dotnet = "dotnet" }

PART 1 - PREPARE THE PRODUCTION LICENSING KEY
==============================================

1.1  Choose a strong production key password.

Use a randomly generated password of at least 24 characters.
Store it in the company password vault, NOT next to the key file and NOT in
this repository. The key generator encrypts the private key with this password.

1.2  Create a secure folder outside the repository.

    $keyDir = "$env:USERPROFILE\Documents\SmartCafeteria-Secrets\production-2026"
    New-Item -ItemType Directory -Force -Path $keyDir | Out-Null
    icacls $keyDir /inheritance:r /grant:r "$env:USERNAME:(OI)(CI)F"

Do NOT use the default key output folder inside the repository.
Do NOT put the production private key in:
  - Activator tool\SmartCafeteria.Activator\keys
  - publish\
  - installer\
  - source control
  - email, chat, logs, or support tickets

1.3  Generate the production keypair.

    $secure = Read-Host "New production key password" -AsSecureString
    $env:SMART_CAFETERIA_KEY_PASSWORD =
        (New-Object System.Net.NetworkCredential('', $secure)).Password

    & $dotnet run --project .\tools\LicenseKeyGenerator\LicenseKeyGenerator.csproj -- `
        --out $keyDir

    Remove-Item Env:\SMART_CAFETERIA_KEY_PASSWORD

The tool writes:

    $keyDir\activator-private-key.pk8   (encrypted PKCS#8, Base64 text)
    $keyDir\license-public-key.spki     (public key, Base64 text)

It also prints:

    Public key Base64: <PRODUCTION_PUBLIC_KEY_BASE64>
    Fingerprint:       <PRODUCTION_FINGERPRINT>

Record the fingerprint and public key Base64 in your release notes.
The private key file is encrypted, but it is still secret.

1.4  Back up the production private key.

- Copy activator-private-key.pk8 to two encrypted backups.
- Keep one backup offline.
- Store the password separately in the password vault.
- Confirm you can restore the key before deleting any development key.

1.5  Put the production public key into the application.

Open this file:

    src\SmartCafeteria.Licensing\Crypto\LicenseKeys.cs

Replace ONLY the Base64 value on the PublicKeyBase64 line with the new
"Public key Base64" printed by the generator. Keep the C# syntax unchanged:

    public const string PublicKeyBase64 =
        "<PASTE_PRODUCTION_PUBLIC_KEY_BASE64_HERE>";

Save the file. Do not add the private key anywhere in the source tree.

Optional verification: run the app build and the licensing tests:

    & $dotnet build .\SmartCafeteria.sln -c Release
    & $dotnet test .\tests\SmartCafeteria.Licensing.Tests\SmartCafeteria.Licensing.Tests.csproj -c Release --no-build

1.6  Remove the development keys.

Back up the old development keys first if you need them for historical test
licenses. Otherwise delete them:

    $devKeys = ".\Activator tool\SmartCafeteria.Activator\keys"
    Remove-Item "$devKeys\activator-private-key.pk8" -Force -ErrorAction SilentlyContinue
    Remove-Item "$devKeys\license-public-key.spki" -Force -ErrorAction SilentlyContinue

Remove copied development keys from all build outputs:

    Get-ChildItem ".\Activator tool\SmartCafeteria.Activator\bin" -Recurse -File `
        -Filter "activator-private-key.pk8" -ErrorAction SilentlyContinue |
        Remove-Item -Force

Check the repository for stray private keys:

    Get-ChildItem -Recurse -File -ErrorAction SilentlyContinue |
        Where-Object { $_.Name -match 'private.*\.pk8$|\.pfx$|\.p12$' } |
        Select-Object FullName

The only .pfx should be your code-signing certificate in a secure folder,
never in this repository.

1.7  Test production activation before signing.

Use a clean test VM or a machine whose license state you can delete.
Production builds are hardware-bound, so generate a request on the actual
test machine.

1. Open Smart Cafeteria and go to Settings -> Activation.
2. Copy the activation request code.
3. Start the Activator tool.
4. Use Browse to select:
       $keyDir\activator-private-key.pk8
5. Enter the production key password.
6. Paste the request, choose Monthly or Permanent, and generate the code.
7. Paste the activation code into Smart Cafeteria and activate.
8. Confirm the status shows the expected license type and expiry.

Also confirm that a code signed with the old development key is rejected.
Because this is a pre-release key replacement, old development licenses are
expected to become invalid. Do not keep the development public key in the
production app.

If you are rotating keys AFTER a public release and must keep old licenses
valid, add the old public key as an additional entry in
LicenseKeys.GetVerificationKeys() for a transition period. Do not do that for
the development key in the first production release.


PART 2 - INSTALL SIGNTOOL AND THE CODE-SIGNING CERTIFICATE
===========================================================

2.1  Install Windows SDK Signing Tools.

Install the Windows 10/11 SDK component:
    "Windows SDK Signing Tools for Desktop Apps"

Typical signtool locations:

    C:\Program Files (x86)\Windows Kits\10\bin\<version>\x64\signtool.exe
    C:\Program Files\Windows Kits\10\bin\<version>\x64\signtool.exe

Find it:

    $signtool = Get-ChildItem "${env:ProgramFiles(x86)}\Windows Kits\10\bin" `
        -Recurse -Filter signtool.exe -ErrorAction SilentlyContinue |
        Where-Object { $_.FullName -match '\\x64\\signtool\.exe$' } |
        Sort-Object FullName -Descending |
        Select-Object -First 1 -ExpandProperty FullName

    if (-not $signtool) {
        throw "signtool.exe not found. Install Windows SDK Signing Tools."
    }

    $signtool

2.2  Use a publicly trusted code-signing certificate.

For distribution, use an OV or EV Code Signing certificate from a public CA.
A self-signed certificate is acceptable only for internal testing.

Most modern OV/EV certificates require a hardware token or HSM. If that is
your case, follow the CA's token instructions and use the certificate from the
Windows certificate store. Do not attempt to export an EV private key.

The certificate must have:
    - Code Signing EKU
    - A valid private key
    - Not expired at signing time

2.3  Preferred: import a .pfx once, then sign by thumbprint.

This avoids putting the PFX password in shell history.

    $pfx = "C:\Secure\codesign.pfx"
    $pwd = Read-Host "PFX password" -AsSecureString
    Import-PfxCertificate -FilePath $pfx `
        -CertStoreLocation Cert:\CurrentUser\My -Password $pwd

    Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
        Sort-Object NotAfter -Descending |
        Format-Table Subject, Thumbprint, NotAfter -AutoSize

    $thumb = "<PASTE_CERT_THUMBPRINT_WITHOUT_SPACES>"

If the certificate is on a hardware token, it normally appears in
Cert:\CurrentUser\My after the token middleware starts. Skip the import and
copy its thumbprint into $thumb.

Direct-PFX alternative (less secure because the password may remain in
PowerShell history):

    & $signtool sign /f $pfx /p "<PFX_PASSWORD>" ...

Prefer the thumbprint method whenever possible.


PART 3 - BUILD AND SIGN THE EXE
================================

3.1  Publish the unsigned single-file Release EXE.

    & $dotnet publish .\src\SmartCafeteria\SmartCafeteria.csproj `
        -c Release -r win-x64 --self-contained true `
        -p:PublishSingleFile=true `
        -p:IncludeNativeLibrariesForSelfExtract=true `
        -p:DebugType=embedded `
        -o .\publish\win-x64

3.2  Sign the EXE.

    $exe = Join-Path $root "publish\win-x64\SmartCafeteria.exe"
    $timestamp = "http://timestamp.digicert.com"

    & $signtool sign `
        /sha1 $thumb `
        /fd SHA256 `
        /td SHA256 `
        /tr $timestamp `
        /d "Smart Cafeteria" `
        $exe

If your CA requires a different RFC3161 timestamp URL, use that URL instead
of the DigiCert URL. Examples:
    http://timestamp.sectigo.com
    http://timestamp.globalsign.com/tsa/r6advanced1

3.3  Verify the EXE signature and timestamp.

    & $signtool verify /pa /all /v $exe

    Get-AuthenticodeSignature $exe |
        Format-List Status, StatusMessage, SignerCertificate, TimeStamperCertificate

Expected:
    Status = Valid
    TimeStamperCertificate is not null

Do not continue if the EXE signature is invalid or has no timestamp.

3.4  PowerShell fallback when signtool.exe is unavailable.

The current release candidate used this method. The certificate is in
Cert:\CurrentUser\My and has a private key:

    $thumb = "A9FC9D49203637ED8492468475EA989F84C6575C"
    $cert = Get-Item "Cert:\CurrentUser\My\$thumb"
    $timestamp = "http://timestamp.digicert.com"

    Set-AuthenticodeSignature `
        -FilePath $exe `
        -Certificate $cert `
        -TimestampServer $timestamp `
        -HashAlgorithm SHA256

    Get-AuthenticodeSignature $exe |
        Format-List Status, StatusMessage, SignerCertificate, TimeStamperCertificate

The PowerShell status can report UnknownError for a self-signed certificate
because the root is not trusted. That is a chain-trust failure, not necessarily
a bad signature. To prove the signature locally, temporarily add the CER to
the CurrentUser Root and TrustedPublisher stores, check for Status=Valid, then
remove it:

    $cer = "C:\Users\user\Documents\SmartCafeteria-Secrets\production-2026\codesign-selfsigned.cer"
    try {
        certutil.exe -addstore -user Root $cer
        certutil.exe -addstore -user TrustedPublisher $cer
        Get-AuthenticodeSignature $exe | Format-List Status, StatusMessage
    }
    finally {
        certutil.exe -delstore -user Root $thumb
        certutil.exe -delstore -user TrustedPublisher $thumb
    }

Do not ship a self-signed certificate as the final public trust anchor. Replace
it with a CA-issued code-signing certificate for distribution.


PART 4 - BUILD AND SIGN THE MSI
================================

4.1  Build the MSI. It reads the signed EXE from:
     publish\win-x64\SmartCafeteria.exe

    & $dotnet build .\installer\SmartCafeteria.Installer.wixproj -c Release

Output:

    installer\bin\x64\Release\SmartCafeteria-Setup-1.0.0.msi

4.2  Sign the MSI.

    $msi = Join-Path $root "installer\bin\x64\Release\SmartCafeteria-Setup-1.0.0.msi"

    & $signtool sign `
        /sha1 $thumb `
        /fd SHA256 `
        /td SHA256 `
        /tr $timestamp `
        $msi

PowerShell fallback used for this release candidate:

    Set-AuthenticodeSignature `
        -FilePath $msi `
        -Certificate $cert `
        -TimestampServer $timestamp `
        -HashAlgorithm SHA256

4.3  Verify the MSI signature and timestamp.

    & $signtool verify /pa /all /v $msi

    Get-AuthenticodeSignature $msi |
        Format-List Status, StatusMessage, SignerCertificate, TimeStamperCertificate

Expected:
    Status = Valid
    TimeStamperCertificate is not null


PART 5 - VERIFY THE MSI PAYLOAD
================================

This confirms the MSI contains the signed EXE, not an older unsigned build.
Administrative extraction does not install the product.

    $check = Join-Path $env:TEMP "SmartCafeteria-msi-check"
    if (Test-Path $check) { Remove-Item $check -Recurse -Force }

    $p = Start-Process msiexec.exe -Wait -PassThru -ArgumentList @(
        "/a",
        "`"$msi`"",
        "/qn",
        "TARGETDIR=`"$check`""
    )

    "msiexec exit code = $($p.ExitCode)"

    $extracted = Get-ChildItem $check -Recurse -File -Filter SmartCafeteria.exe |
        Select-Object -First 1

    Get-AuthenticodeSignature $extracted.FullName |
        Format-List Status, SignerCertificate

    Test-Path (Join-Path $extracted.DirectoryName "install.marker")

    Remove-Item $check -Recurse -Force

Expected:
    msiexec exit code = 0
    Extracted EXE Status = Valid
    install.marker = True


PART 6 - RECORD FINAL HASHES
=============================

Signing changes the hashes. Compute hashes AFTER all signing is complete.

    Get-FileHash $exe, $msi -Algorithm SHA256 |
        Format-Table Path, Hash -AutoSize

Record in PROGRESS.md:
    - production public-key fingerprint
    - final EXE size and SHA256
    - final MSI size and SHA256
    - signing certificate subject and thumbprint
    - date signed

Do not record the private key or its password in PROGRESS.md.


PART 7 - OPTIONAL: SIGN THE ACTIVATOR TOOL
===========================================

The Activator is vendor-only and should not be distributed to customers.
If you distribute a compiled Activator, sign it too:

    $activator = ".\Activator tool\SmartCafeteria.Activator\bin\Release\net10.0-windows\SmartCafeteria.Activator.exe"

    & $signtool sign `
        /sha1 $thumb `
        /fd SHA256 `
        /td SHA256 `
        /tr $timestamp `
        /d "Smart Cafeteria Activator" `
        $activator

    & $signtool verify /pa /all /v $activator

Never copy the production private key into the Activator project's keys
folder. Browse to the key in the secure folder when you use the Activator.

PART 9 - COMMON FAILURES
=========================

"signtool is not recognized"
    Install Windows SDK Signing Tools, or invoke signtool by its full path.

"No certificates were found that meet all the given criteria"
    The thumbprint is wrong, the private key is missing, or the certificate
    does not have the Code Signing EKU. Check:
        Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert

"SignTool Error: No file digest algorithm specified"
    Add /fd SHA256.

Timestamp error
    Retry with your CA's RFC3161 timestamp URL. A signature without a trusted
    timestamp stops being valid when the certificate expires.

MSI contains an unsigned EXE
    You built the MSI before signing the EXE, or you republished after signing.
    Sign the EXE again, rebuild the MSI, then sign the MSI.

The MSI signature is gone after a rebuild
    Rebuilding replaces the MSI. Sign it again.

SmartScreen still warns
    A new certificate has no reputation yet. EV certificates usually help.
    Code signing is still required even when SmartScreen warns initially.

Hardware token not found
    Start the token middleware as the same Windows user, confirm the certificate
    is in Cert:\CurrentUser\My, and use the x64 signtool.exe.
